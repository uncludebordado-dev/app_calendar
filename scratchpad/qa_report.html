BUG-001
Crítica P0 Corregido · 1 paso tuyo pendiente

Secreto del webhook de email, hardcodeado y filtrado en el repo público

Módulo
Integración de emails (Database Webhook → Edge Function)
Archivo
supabase/CONECTAR_EMAILS.sql
Detectado por
git grep del valor + consulta a la API pública de GitHub

Qué encontré

El valor real de EMAIL_WEBHOOK_SECRET estaba escrito en texto plano dentro de un .sql que subimos a git. Confirmé con la API de GitHub que el repo es público ("private": false), así que ese secreto era visible para cualquier persona con el link, sin necesidad de tener acceso a Vercel ni a Supabase.

Riesgo

Con ese secreto, cualquiera puede llamar directo a la Edge Function send-booking-emails y hacerle mandar un mail con el remitente de tu marca a cualquier dirección — la función arma el to a partir de lo que venga en el body, sin cruzarlo contra la base. En la práctica: tu cuenta de Resend se puede usar como "reenviador" para spam o phishing, con tu dominio y tu cupo.

Cómo se reproducía

  1. Abrir supabase/CONECTAR_EMAILS.sql en GitHub (público, sin login).
  2. Copiar el valor de x-webhook-secret.
  3. POST a la URL de la función con ese header + un body.record armado a mano.
  4. La función responde 200 y dispara el mail.
Arreglado

El secreto ya no vive en ningún archivo (ni siquiera local): se guarda en private.app_secrets, una tabla sin permisos para anon/authenticated que sólo lee la función SECURITY DEFINER que dispara el webhook. El archivo del repo quedó con un placeholder y las instrucciones para cargarlo sin commitearlo.

Commit fa24c82

Pendiente de vos

El valor viejo queda inútil recién cuando lo rotás: generá un secreto nuevo, cargalo en Supabase → Edge Functions → send-booking-emails → Secrets → EMAIL_WEBHOOK_SECRET, y pegá ese mismo valor en el bloque de CONECTAR_EMAILS.sql (sin subirlo a git). Te paso el paso a paso apenas quieras.

BUG-002
Crítica P0 Corregido

Next.js 15.1.0 vulnerable a bypass del middleware (CVE-2025-29927)

Módulo
Framework — protección de rutas privadas
Afectaba a
Todo lo que depende de middleware.ts: /admin/*, /calendario, /mis-reservas…

Qué encontré

La versión de Next instalada (15.1.0) tiene una vulnerabilidad pública conocida que permite saltear la ejecución del middleware con un header especial en la request, llegando a rutas que deberían estar bloqueadas para quien no inició sesión.

Riesgo

El middleware es la primera barrera que protege /admin. Con esta falla, alguien podía en teoría esquivarla — igual quedaba la segunda barrera (cada página vuelve a chequear requireAdmin() del lado del servidor), pero no había que depender de eso.

Arreglado

Next actualizado 15.1.0 → 15.5.25 (dentro de la misma serie, sin cambios de API). Verifiqué después del build que /admin sin sesión sigue devolviendo 307 a /login.

Commit 411b91a

BUG-003
Alta P1 Corregido

/api/health exponía la configuración del servidor sin pedir nada

Módulo
API de diagnóstico (temporal, de cuando armamos las keys)
Archivo
src/app/api/health/route.ts (eliminado)

Qué encontía

Una ruta sin login devolvía, para cada variable de entorno sensible (incluida la service role key de Supabase): si estaba presente, su longitud, sus primeros y últimos caracteres, y si tenía espacios raros. No mostraba el valor completo, pero sí confirmaba que existía y daba pistas de su forma — información que no debería estar a un click de cualquiera.

Arreglado

Se borró la ruta entera. Cumplió su función cuando depurábamos el problema de las keys pegadas mal; ya no hace falta con la app en producción y datos reales de alumnas.

BUG-004
Alta P1 Corregido

El panel de "Alumnas" no mostraba a nadie por un choque de tipos en SQL

Módulo
Base de datos — funciones del panel de administración
Funciones
admin_students_overview, admin_rosters_between, admin_list_students, admin_month_summary

Qué encontré

Estas funciones declaraban su columna email como text, pero la traían de auth.users.email, que en Postgres es varchar(255). Postgres es estricto con eso dentro de un RETURNS TABLE: compila bien, pero explota en tiempo de ejecución.

Cómo lo reproduje

POST /rest/v1/rpc/admin_students_overview
→ 42804: structure of query does not match function result type
  "Returned type character varying(255) does not match expected type text
   in column 3"

Lo confirmé generando una sesión real de admin (magic link + verify por API) y llamando la función tal cual la llama la app — no era un supuesto, se reproducía siempre.

Impacto para el negocio

"Alumnas" aparecía vacío, la ficha de cada una no cargaba, y al editar un horario la lista de inscriptas tampoco — sin ningún error visible para el admin, sólo listas vacías.

Arreglado

Cast explícito u.email::text en las 4 funciones.

BUG-005
Media P2 Corregido

Un doble clic en el puntito podía registrar el cobro dos veces

Módulo
Base de datos — admin_toggle_paid()
Tipo
Condición de carrera (TOCTOU)

Qué encontré

La función marcaba "pagó" así: primero preguntaba si ya existía un pago para esa reserva (if exists…) y, según la respuesta, insertaba o actualizaba. Entre esas dos consultas hay una ventana: dos clicks casi simultáneos (o una red lenta que hace reintentar) podían colarse ahí y terminar en dos filas de pago para la misma clase, inflando "Total recaudado".

payments.booking_id no tenía ninguna restricción de unicidad que lo impidiera.

Arreglado

Constraint unique (booking_id) (permite muchos NULL, para los pagos manuales sin reserva asociada) + la función reescrita con INSERT … ON CONFLICT (booking_id) DO UPDATE: ahora es una sola operación atómica, sin ventana entre leer y escribir.

BUG-006
Media P2 Corregido

La planilla exportada podía traer una fórmula sin que nadie la haya escrito ahí

Módulo
/admin/export (descarga de asistencias y dinero)
Categoría
CSV / Formula Injection (CWE-1236)

Qué encontré

El CSV escapaba comillas y saltos de línea, pero no los caracteres = + - @ al principio de un campo. Si una alumna se registrara con un nombre como =HYPERLINK("http://...","click"), Excel/Sheets lo abre como fórmula, no como texto — un vector clásico para links falsos o, en configuraciones viejas, ejecutar comandos.

Arreglado

Cualquier celda que empiece con =, +, -, @ o tab ahora se antepone con un apóstrofe antes de exportar, así la hoja de cálculo la trata siempre como texto plano.

Commit fa24c82

BUG-007
Media P2 Corregido

Las fotos de perfil sólo se validaban en el navegador

Módulo
Supabase Storage — bucket avatars

Qué encontré

El límite de 4 MB y el filtro "sólo imágenes" vivían en el componente de React. La policy de Storage sólo controla quién puede escribir en qué carpeta, no qué sube — alguien llamando directo a la API de Supabase (saltándose la web) podía subir un archivo de cualquier tamaño o tipo a su propia carpeta.

Arreglado

El bucket ahora tiene file_size_limit = 4 MB y allowed_mime_types restringido a image/jpeg, png, webp, gif — la restricción vive en el servidor, no sólo en el formulario.

BUG-008
Informativo P3 No es bug — a tener en cuenta

El PIN de "Privacidad y seguridad" no protege la cuenta, sólo la pantalla

Módulo
src/lib/pin.ts

Es un candado local: el PIN se guarda (hasheado) en el localStorage de ese celular, para que alguien que agarre el teléfono desbloqueado no vea la app. No reemplaza el login de Supabase ni protege si alguien tiene la cuenta real. Está bien diseñado y comentado así en el código — lo anoto para que quede documentado, no porque haya que arreglar nada. Si te sirve, se podría aclarar con una frase en la pantalla de "Privacidad" para que quede clarísimo también para quien lo usa.

02

Cómo testear esta app como profesional

Una guía corta para arrancar en QA usando esta app como terreno de práctica real: tiene autenticación, roles, dinero, fechas, storage y una PWA — el combo típico que te vas a encontrar en cualquier producto.

01

Mentalidad: explorá con una misión, no al azar

Un "charter" de testing exploratorio es una frase que dice qué vas a investigar y con qué objetivo, por ejemplo: "Explorar el flujo de cancelación de reserva, buscando qué pasa cerca del límite de 48 h, durante 30 minutos." Anotá lo que ves, no sólo los bugs — también lo confuso, lo lento, lo que te sorprendió.

Técnicas: partición de equivalencia · valores límite · tablas de decisión
02

Un plan de test manual, específico para esta app

Cuatro zonas con lógica propia que vale la pena recorrer a mano antes de automatizar nada:

Reservas y cupo

  • Reservar la última plaza de una clase (cupo → 0) y que la siguiente persona vea "completo", no un error feo.
  • Dos pestañas reservando la última plaza casi al mismo tiempo — sólo una debería ganar.
  • Cancelar antes y después de las 48 h: confirmar que sólo suma sanción en el segundo caso.
  • Acumular 3 sanciones → cuenta bloqueada → admin la "perdona".

Roles y permisos

  • Con sesión de alumna, pegar en la barra una URL de /admin/... a mano.
  • Ver si una alumna puede leer datos de otra cambiando un ID en la URL o en una llamada de red.
  • Cerrar sesión en medio de una acción (reservar, pagar) y ver qué mensaje da.

Dinero y fechas

  • Marcar "Pagó" y "No pagó" varias veces seguidas, rápido — el total no debería desincronizarse.
  • Probar el mes límite (septiembre 2026): la flecha "mes anterior" no debe dejar ir más atrás.
  • Registrar un cumpleaños el 29 de febrero, o el mismo día de hoy, y ver el aviso.
  • Cambiar la fecha/hora del sistema del celular y ver si algo se rompe (reservas, "hoy").

Multiplataforma

  • Instalar la PWA en Android y en iPhone — son flujos distintos.
  • Probar con la conexión cortada (modo avión) después de instalarla.
  • Ancho 360 px, texto agrandado del sistema, y con el teclado abierto tapando un botón.
  • Modo claro/oscuro, y con "reducir movimiento" activado en el sistema.
03

Testeá el backend directo, sin pasar por la pantalla

Esta app corre sobre Supabase: Postgres con permisos (RLS) + funciones remotas (RPC) + Storage. Se puede probar esa capa aparte de la interfaz, con una herramienta de requests — es exactamente cómo confirmé el BUG-004 de este informe: no adiviné que fallaba, se lo pedí directo a la API y vi el error.

  • Con la anon key: probá leer una tabla sin estar logueada — RLS debería devolver vacío, no error.
  • Con el token de una alumna real (te lo da el login): probá llamar una función de admin — debería rechazarla.
  • Mandá tipos de dato raros a propósito: un amount negativo, una fecha con formato roto, un texto de 5000 caracteres en un campo que espera 160.
Herramientas: Postman · Insomnia · Thunder Client (VS Code) · curl
04

Cómo reportar lo que encontrás

Un bug que nadie puede reproducir es un bug que no se arregla. Usá una plantilla fija — las fichas de la Parte 1 de este informe siguen esta estructura a propósito:

Plantilla

Título — una frase que diga el síntoma, no la causa ("El total se duplica al tocar Pagó dos veces rápido", no "Bug en pagos").

Severidad vs. Prioridad — no son lo mismo: severidad es cuánto daño hace; prioridad es cuándo conviene arreglarlo. Un typo en la portada puede ser prioridad alta (lo ve todo el mundo) con severidad baja.

Pasos para reproducir — numerados, desde cero (sesión limpia, datos de ejemplo).

Esperado vs. Actual — las dos frases, una al lado de la otra.

Entorno — navegador, tamaño de pantalla, con qué usuario.

05

El camino hacia la automatización

No automatices todo de una — empezá por donde un bug te cuesta más caro si vuelve a pasar:

  • 1º — El camino crítico end-to-end: registro → completar perfil → reservar → cancelar. Un solo test que recorre todo el viaje de la alumna.
  • 2º — Reglas de negocio puntuales: la ventana de 48 h, el cupo máximo, el bloqueo por 3 sanciones.
  • 3º — Accesibilidad automática en cada página nueva (no reemplaza probar con teclado y lector de pantalla, pero atrapa lo obvio rápido).
  • 4º — Tests de API/RPC directos contra Supabase, sin abrir un navegador — son los más rápidos y estables de mantener.
Herramientas: Playwright o Cypress (end-to-end) · axe-core / Lighthouse CI (accesibilidad) · Vitest + supabase-js (tests de API) · GitHub Actions (correrlos solos en cada cambio)
